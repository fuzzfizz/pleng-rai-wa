# Should-Fix Workflow (กระบวนการแก้ไขบั๊กและปรับปรุงระบบจาก should fix.md)

กระบวนการมาตรฐานสำหรับการจัดการบั๊กและรายการปรับปรุงจากไฟล์ `should fix.md` ในโปรเจกต์ เพลงไรวะ (Pleng-Rai-Wa)
ผู้ช่วย AI (Agent) **ต้องปฏิบัติตาม 5 ขั้นตอน (Phases) นี้อย่างเคร่งครัดตามลำดับเสมอ**:

```
[Phase 1: อ่าน & ซักถามจนเข้าใจ] 
       ↓
[Phase 2: จัดลำดับความสำคัญ] 
       ↓
[Phase 3: วิเคราะห์สาเหตุ & วางแผน -> รอ User อนุมัติ] 
       ↓
[Phase 4: ดำเนินการด้วย Subagent & รายงานทีละ Task] 
       ↓
[Phase 5: ทดสอบ Build, อัปเดต should fix.md & Push ขึ้น GitHub]
```

---

## Phase 1: Deep Understanding & Relentless Clarification (ทำความเข้าใจ & ซักถามจนเข้าใจแจ่มแจ้ง)

1. **อ่านไฟล์ `should fix.md` อย่างละเอียดทุกบรรทัด:**
   - ตรวจสอบรายการปัญหาและข้อกำหนดทั้งหมด
   - ค้นคว้าโค้ดในโปรเจกต์ที่เกี่ยวข้องเพื่อดูสภาพแวดล้อมจริง
2. **หากมีข้อสงสัยหรือไม่เข้าใจจุดใด ต้องถามทันที:**
   - **กฎเหล็ก:** ห้ามเดาหรือสมมุติเอาเองเด็ดขาด *"ไม่เข้าใจส่วนไหนให้ถามจนกว่าจะเข้าใจปัญหา"*
   - ตั้งคำถามอย่างเจาะจง ระบุทางเลือก หรือขอยกตัวอย่างสถานการณ์ที่เกิดปัญหาจนกว่าจะได้ข้อสรุปที่ชัดเจน 100%

---

## Phase 2: Problem Prioritization (จัดลำดับความสำคัญของปัญหา)

ก่อนเริ่มเขียนแผน ให้จัดหมวดหมู่และเรียงลำดับความสำคัญของปัญหา:
1. **Critical / Blocker:** บั๊กที่ทำให้เล่นต่อไม่ได้ เกมค้าง เฉลยผิด หรือคำนวณคะแนนผิด
2. **Gameplay / Functional:** กลไกการเล่นเกมไม่ตรงตามกติกา เช่น สิทธิ์การตอบ การจับเวลา การวนเพลงซ้ำ
3. **UX / UI Ergonomics:** ความสะดวกในการเล่น เช่น การเลื่อนลูกศร Autocomplete, การแสดงผลบนจอทีวี, ป้ายแจ้งเตือน
4. **Settings / Configuration:** ตัวเลือกในหน้าตั้งค่าห้อง, การซิงค์สถานะ Real-time ระหว่างผู้เล่น

---

## Phase 3: Root Cause Analysis & Plan Proposal (วิเคราะห์สาเหตุ & นำเสนอแผนให้ผู้ใช้ตรวจสอบ)

1. **เจาะลึกหาสาเหตุที่แท้จริง (Root Cause Analysis):**
   - ตรวจสอบบรรทัดโค้ดจริง ฟังก์ชัน และ State ที่ก่อให้เกิดปัญหา
   - ระบุไฟล์และบรรทัดที่เกี่ยวข้องเป็น clickable markdown links เสมอ เช่น `[game-view.tsx](file:///D:/pleng-rai-wa/src/components/room/game-view.tsx#L100-L120)`
2. **ร่างแผนการแก้ไขปัญหา (Implementation Plan):**
   - สรุปแต่ละข้อให้ชัดเจน:
     - **สาเหตุของปัญหา (Root Cause)**
     - **แนวทางการแก้ไข (Proposed Solution)**
     - **แผนการทดสอบ (Verification Plan)**
3. **นำเสนอแผนให้ผู้ใช้ตรวจพิจารณา:**
   - นำเสนอแผนอย่างเป็นระเบียบ อ่านง่าย
   - **หยุดรอคำสั่งจากผู้ใช้ ("เมื่อฉันสั่งให้แก้ไขได้") ก่อนเริ่มแตะต้องโค้ดการแก้ไขจริงเสมอ**

---

## Phase 4: Subagent-Driven Execution (ทำงานด้วย Subagent & รายงานผลทีละ Task)

เมื่อผู้ใช้ส่งสัญญาณอนุมัติ (เช่น *"ลงมือได้เลย"*, *"เริ่มแก้ได้"*, *"ดำเนินการตามแผน"*):

1. **แบ่งงานออกเป็นกลุ่มงาน (Cohesive Tasks):**
   - แยกกลุ่มงานที่แก้ไขไฟล์เดียวกันหรือเป็นอิสระต่อกัน เพื่อป้องกันปัญหา Conflict
2. **เรียกใช้ Subagent ผ่าน `invoke_subagent`:**
   - มอบหมายงานให้ Subagent จัดการอย่างเฉพาะเจาะจง
   - Subagent จะรับผิดชอบการแก้ไขไฟล์และรัน Unit Test ประจำโมดูล
3. **รายงานความคืบหน้าให้ผู้ใช้ทราบอย่างต่อเนื่อง:**
   - อัปเดตสถานะให้ผู้ใช้เห็นว่าแต่ละ Task เสร็จสิ้นแล้วอย่างไร จนกว่าจะครบทุกข้อ

---

## Phase 5: Verification, Documentation & GitHub Push (ทดสอบ, บันทึกผล และ Push)

1. **รันการทดสอบแบบครบวงจร (100% Verification):**
   - รัน Unit Tests ทั้งหมด: `npx vitest run` (ต้องผ่าน 100% ไม่มี fail)
   - รัน Next.js Production Build: `npm run build` (ตรวจสอบ Type check และ Bundle สำเร็จ 0 errors)
2. **อัปเดตไฟล์ `should fix.md`:**
   - บันทึกสถานะ `[แก้ไขแล้ว ✓]` สำหรับทุกข้อที่จัดการเสร็จสิ้น
   - บันทึกสรุปสาเหตุ (Root Cause) และแนวทางการแก้ไขลงในเอกสาร
3. **Git Commit & Push ขึ้น GitHub:**
   - Stage ไฟล์และ commit ด้วย Semantic commit message เช่น:
     `git commit -m "fix(audio-slice): <คำอธิบายสั้นๆ เกี่ยวกับการแก้ไข>"`
   - สั่ง Push การเปลี่ยนแปลงขึ้น Remote Repository ทันที:
     `git push origin main`
   - แจ้งยืนยันสถานะ commit hash และ git branch ให้ผู้ใช้ทราบเป็นขั้นตอนสุดท้าย
